1Problem statement

A small record shop sells three kinds of items: vinyl records, numbered limited-edition vinyls and cassettes. Every item has a name, a price and a stock count. The shop needs to add items, search for them, restock them, sell them, play a preview and give discounts.

Wrong data must be stopped. A price can not be negative, stock can not go below zero, and a sale can not ask for more copies than the shop has. When that happens, the program throws an exception with a clear message and the stored values stay the same.

How the program is organised

When it starts, the program welcomes you to the shop. You can browse the records, pick one, see its track list and play tracks with a progress bar, add records to a cart and buy them. A separate menu option opens the eight OOP topics, one for each part of the syllabus. Each topic runs a short demonstration that uses the store's classes and prints labelled results, so any team member can run one topic and explain the code behind it.

2.1Use case diagram

Two kinds of people use the store. Customers browse, search, play previews and buy. Staff add products, restock, change prices and give discounts. Buying always includes a stock check. The out-of-stock error only happens when the check fails, which is why it is an «extend».

Figure 1. Use case diagram. «include» means always done as part of the use case; «extend» means done only in a special case.

2.2Class diagram: products and interfaces

Product is abstract and holds what every item shares. VinylRecord and Cassette extend it (hierarchical inheritance), and LimitedEdition extends VinylRecord (multilevel inheritance). VinylRecord implements two interfaces at once, which is how Java gets multiple inheritance. Collectible extends Discountable, so LimitedEdition must write both getCertificate() and applyDiscount().

Figure 2. Product hierarchy. The overloaded restock() and the three VinylRecord constructors appear as separate lines in the operations compartment.

2.3Class diagram: shop app, store and helpers

Main shows the welcome menu and hands the shop screens to StoreApp. StoreApp fills the Store with six records, each with its own Track[], and runs browsing, playing, the cart and buying. Store is a Singleton: its constructor is private, and getInstance() always returns the same object. Store.Receipt is a static nested class and Store.Cart is an inner class. Each Product owns its tracks (composition). Track has no constructor of its own, so Java gives it a default one.

Figure 3. Main, StoreApp, Store, its nested classes and Track. Product is shown with its compartments hidden; Figure 2 has the full box.

2.4Class diagram: exceptions

Both custom exceptions extend Java's built-in classes. OutOfStockException extends Exception, so it is checked: whoever calls sell() must catch it. InvalidPriceException extends RuntimeException, so it is unchecked.

Figure 4. Exception classes. sell() throws OutOfStockException; setPrice() throws InvalidPriceException.

2.5Object diagram

This is memory after Topic 1 runs VinylRecord c = a; and c.setStock(99). No new object was made, so a and c point to the same object and both see stock 99. b is a separate object with its own values.

Figure 5. Object diagram. Object names are underlined, in the form objectName : ClassName.

2.6Sequence diagram: creating a limited edition

Creating new LimitedEdition(...) runs the constructors from the top parent down. Each constructor's first line calls super(...), so the Product part is set up first and the LimitedEdition part last.

Figure 6. Constructor chain, shown as self-calls because it all happens inside one object. Run java -cp out Main 4 to see the same order printed.

2.7Sequence diagram: selling a record

The shop has 3 copies. sell(2) succeeds. sell(10) creates an OutOfStockException and throws it back to Main, which catches it. The finally block runs both times.

Figure 7. Sequence diagram for Topic 8. Solid arrows are calls; dashed arrows are returns, a throw, or creating an object.

2.8Activity diagram: sell inside try / catch / finally

Figure 8. Both paths meet before finally, so it always runs, whether the sale works or throws.

5Limitations and future work

  • Data is created in code and is lost when the program ends. Saving to a file would keep it.
  • Playback is simulated with a sped-up progress bar; real audio would need a sound library.
  • More product types, such as CDs or gift cards, would only need a new class that extends Product.
